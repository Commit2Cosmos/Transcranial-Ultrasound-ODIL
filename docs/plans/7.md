## Objective
A new planning run (no task PR yet) passes the `report` job only if one of
these exists:

- (a) Plan published: the remote branch `agent/issue-N` exists, it contains
  `docs/plans/N.md`, and an open draft PR exists from that branch.
- (b) Clarification posted: a clarification comment exists on issue N that is
  correlated with this exact invocation.

Otherwise the job posts a fixed, actionable notice and fails with
`PLAN_NO_DELIVERABLE`. A fresh `@claude plan` comment is the supported
recovery path. If invocation metadata is missing or inconsistent, the job must
fail clearly.

This is local bootstrap maintenance. It is planned and implemented in a local
Claude Code session, not by the hosted agent repairing itself.

## Proposed approach
### Invocation identity
- `setOutputs` receives `runId` (`context.runId`) and `runAttempt`
  (`GITHUB_RUN_ATTEMPT`) in the claude job's Re-resolve step.
- It adds two outputs:
  - `run_attempt`;
  - `invoked_at`: the ISO time recorded just before Claude starts.
- For new planning runs, `buildPrompt` adds an instruction: a clarification
  comment must end with the exact line
  `<!-- claude-task:clarification run=<runId> attempt=<attempt> -->`.
- `clarificationMarker` throws if the run ID or attempt is not a positive
  integer, so a run with a bad identity fails before Claude starts.

### Completion check (`checkPlanDeliverable`)
The report job runs this check only when the profile is `plan`, there is no
PR number, and the Claude job succeeded.

1. Publication state, read from the remote:
   - the branch SHA (`branchSha`);
   - `repos.getContent(docs/plans/N.md, ref: <branch SHA>)` must return a
     file;
   - the open PRs from `owner:agent/issue-N`.

   If the branch, the plan and an open draft PR all exist, the run passes.
   This does not depend on invocation metadata: the gate already guarantees
   that no task PR existed before the run.
2. Invocation metadata. All of these must hold:
   - `run_attempt` is a positive integer equal to the report job's
     `GITHUB_RUN_ATTEMPT`;
   - `invoked_at` is a valid timestamp and not later than the check.

   If any of these fails, clarification is "unverifiable" and the reason is
   stated (for example, "claude job attempt 1, report attempt 2"). The check
   goes on to step 4 without searching for comments.
3. Clarification. List the issue comments updated since `invoked_at`. Accept a
   comment only if all of these hold:
   - the author is `claude[bot]` with type `Bot`;
   - `created_at` is at or after `invoked_at`;
   - the body contains the marker for this run ID and attempt;
   - after the marker is removed, at least one line is 15 or more characters
     long, contains a letter and contains `?`.

   Other bots, humans, earlier attempts, other runs and unmarked comments are
   rejected.
4. If neither (a) nor (b) holds, post a fixed notice on issue N. The notice
   contains:
   - a first line starting `PLAN_NO_DELIVERABLE`;
   - the run link with the attempt;
   - the branch: found or not found;
   - the plan file: present, missing, or not checked;
   - the open draft PR: none, #n, or "#n is open but not a draft";
   - the clarification result: "none found", or "unverifiable: <reason>";
   - "The workflow does not know why the agent stopped."
   - "Inspect any branch or PR, then comment `@claude plan` for a fresh
     invocation."

   Then call `core.setFailed('PLAN_NO_DELIVERABLE: branch=… plan=… pr=… clarification=…')`.

   The notice contains no agent output.

This replaces the existing "pushed but no draft PR" message. The case where
the branch exists but the plan or the PR is missing is now reported through
the same notice.

### Workflow (`claude.yml`)
- Re-resolve passes the run ID and attempt.
- The claude job gets `outputs: run_attempt, invoked_at` from
  `steps.resolve`.
- The report job gets env `CLAUDE_OUTPUTS: ${{ toJSON(needs.claude.outputs) }}`
  and passes the parsed value to `report` as `claude`.
- `claude_args` ends with `--model opus` exactly once. `profileArgs` never
  emits `--model`.
- The comment above the report job is updated.

### Recovery and limitations (docs)
- The supported recovery is a fresh `@claude plan` comment.
- "Re-run failed jobs" on only the report job reuses the claude job outputs
  from an earlier attempt. That is reported as unverifiable, not accepted.
- These still pass on the job result alone:
  - plan revisions on an existing PR;
  - read-only requests;
  - implementation runs.
- Partial failures and question quality are not judged.

### Alternatives considered
- Accept any `claude[bot]` comment created after the event. Rejected: it does
  not tie the comment to an invocation, and it accepts unrelated output.
- Require a commit on every run. Rejected: clarification is a valid outcome,
  and the other profiles have different deliverables.

## Acceptance criteria
`node --test .github/scripts/claude-task.test.js` passes. It includes tests
showing these behaviours:

- No branch and no comment → notice posted, job fails with
  `PLAN_NO_DELIVERABLE`.
- A correctly marked comment from an unrelated author fails:
  `github-actions[bot]`, another `[bot]`, or a human named `claude`.
- A `claude[bot]` comment from a different invocation fails: a different run
  ID, a different attempt, no marker, or created before `invoked_at`.
- A correlated marker without question content fails.
- A valid correlated clarification passes, and no notice is posted.
- Partial publication fails:
  - the branch exists but the plan is missing;
  - the plan exists but there is no PR;
  - the PR is open but not a draft;
  - the plan exists only on another ref.
- A fully published plan passes, including when invocation metadata is
  missing.
- Missing or invalid `invoked_at` or `run_attempt`, or a claude attempt that
  differs from the report attempt, fails with "unverifiable: <reason>" and
  never accepts a clarification.
- Plan revisions, read-only runs and failed Claude jobs keep their existing
  behaviour.
- The prompt contains the marker only for new planning runs, and a bad run
  identity throws.
- `profileArgs` output never contains `--model`.

Also required:
- Mutation check: removing any one of these conditions makes at least one test
  fail:
  - the author check;
  - the timing check;
  - the marker check;
  - the question check;
  - the plan/draft check;
  - the metadata-consistency check.
- The final `claude_args` for each profile contains `--model` exactly once, and
  the pinned action's parser yields `model: "opus"`.
- The notice and the failure message contain no agent output.
- No application code or `claude-code-review.yml` changes.

## Risks and open questions
These are unverified until the live smoke tests:
- which model `opus` resolves to;
- whether job outputs from an earlier attempt are reused on "re-run failed
  jobs";
- how `issues.listComments` `since` filtering behaves (it is only a
  prefilter: `created_at` is re-checked).

Other risks:
- The agent may post a clarification without the marker. The run then fails
  with a notice. That is the intended conservative outcome: retry with a fresh
  `@claude plan`.
- A plan pushed and a PR opened after a concurrent run cannot be told apart
  from this run's output. Per-task concurrency and the gate's duplicate check
  make this unlikely.
- Approval mechanics for this bootstrap task: a `@claude approve-plan` comment
  on this PR would start the hosted agent. Implementation approval for this
  task is therefore given to the local session, naming the plan's full commit
  SHA.
